One process.
Direct to the machine.

LiNC is a Rust and egui HMI for LinuxCNC. Its backend worker owns the NML and HAL links in-process, so the control path is a typed command in and a sampled machine state out. No Python helper. No JSON bridge.

The whole backend contractcrates/linc-core/src/backend.rs
pub trait MachineBackend: Send + 'static {
    fn snapshot(&mut self) -> MachineSnapshot;
    fn send(&mut self, command: MachineCommand)
        -> Result<(), MachineError>;
}
Why it holds

Two verbs, no escape hatch.

snapshot is state. send is intent. There is no generic NML or HAL write in the contract, so a page cannot invent a machine action that the command set does not describe.

BackendHandle turns this into a cloneable UI handle: an mpsc command channel in, a mutex-protected snapshot and event queue out.

03 / COMMAND PATH
Intent

The screen proposes. The controller disposes.

Every machine action the HMI initiates is expressed as a closed MachineCommand and crosses the worker channel. The backend dispatches it with explicit guards on motion, offsets and writes; the command set itself bounds what can be asked. Motion authority still belongs to the physical panel and the LinuxCNC task.

Command lane asynchronous · typed · auditable

  3. 03BackendHandleid allocated · sent over mpsc
  4. 04linc-backendworker receives and owns the call
  5. 05NmlBackendstate and safety checks · dispatch

Representable actions

A deliberately small vocabulary

IssueMdi IssueToolChange LoadTool ConfirmManualToolChange SetCurrentTool LoadProgram SaveProgram SetWorkOffset SetG92Offset ZeroWorkOffset SetWorkPosition SetToolTableRow ApplyProbeResult ResetProbeCalibration SetHalOutput RunFromLine AbortProgram ToggleLimitsOverride ClearTrail

The command set is intentionally narrower than LinuxCNC's API. That is the safety mechanism, not an implementation shortcut.

Not representable

No on-screen machine panel

cycle start jog spindle coolant feed override rapid override spindle override software E-stop

These belong to the panel service and HAL. The explicit exceptions are MDI, RUN PROBE, CHANGE TOOL, RUN FROM LINE, and the keyboard Esc program reset while a program is active.

Validation surfaces

What has to be true before the command moves

GateWhat it protectsWhere it lives

Gates are per command, not global. LoadProgram only refuses while a program is running, and ToggleLimitsOverride goes straight to NML. The strongest checks guard motion and writes that can move or destroy work.

Known latency edge: NmlClient is not Sync, so one client lives on the worker. Mode switches and offset read-back call wait_complete, which can delay snapshots while the controller settles. Splitting status and command clients is the next robustness step if that wait starts to matter.
04 / FEEDBACK PATH
State

State is sampled, not pushed through a codec.

On every tick the backend reads the controller's status, HAL feedback and the parameter file, builds one immutable MachineSnapshot, then publishes it under a mutex. The UI draws the latest complete picture.

Snapshot lane configured 10–20 Hz · default 20 Hz
  1. 01poll_status()emcStatus from NML
  2. 02read feedbackHalReader + parameter file + panel
  3. 03SnapshotBuildernormalise units, offsets, tools, alarms
  4. 04MachineSnapshotone complete immutable value
  5. 05publishmutex swap · generation++ · notify
  6. 06egui frameread latest · repaint
Inputs

Three live sources

NML status carries task state, pose, offsets, feed and spindle data. HAL pins add the panel, pendant and spindle feedback. The parameter file supplies persisted work offsets and probe values.

Output

One typed snapshot

Axes, panel, spindle, program, offsets, tools, alarms, probe result, tool trail, bridge health and HAL selections arrive together. The UI never assembles machine state from several unsynchronised sources.

Failure signal

Staleness is explicit

When the NML status link fails, the backend marks meta.stale, sets the panel offline, records the bridge error and keeps the last snapshot. It does not silently clear the state.

    • 05 / INTEGRATION SURFACES
    Contact points

    Four surfaces, four owners.

    NML carries controller commands and status. HAL carries panel, spindle and typed HMI outputs. The filesystem carries parameters and programs. Unix sockets carry diagnostics. Each has a different permission model.

    NML

    read + write
    • emcStatus polled by the worker
    • emcCommand queued by NmlClient
    • emcError drained into messages
    • links liblinuxcnc.a + libnml.so

    HAL

    read + constrained write
    • HalReader reads arbitrary pins
    • cnc_panel.* from the panel service
    • linc.* from LincHal, five outputs
    • no generic HAL write exists

    Files

    read + write
    • parameter file for G54–G59.3, G92, probe
    • program text for load / save
    • tool table with P words
    • ordinary std::fs, no helper

    Diagnostics

    read-mostly
    • Unix socket per LiNC role
    • linc-mcp attaches over linc-diag
    • snapshot, frames, events, crash records
    • simulator writes are opt-in twice

    The five HAL outputs

    PinTypeBehaviour
    linc.hmi-alivebitToggles every 500 ms; drops false on shutdown.
    linc.tool-change-confirmbitHeld as a level while the manual change confirmation stands.
    linc.status-displays32On change or at 5 Hz; -1 when no two-digit value is available.
    linc.jog-incrementfloatSelected increment in machine units; 0.0 is continuous.
    linc.jog-speedfloatINI linear velocity scaled by the HMI jog percentage.

    Parameter-file mapping

    # LinuxCNC fixes these numbered parameters
G54..G59.3 5200 + index×20 + 1..9
rotation   5200 + index×20 + 10
G92        5211 .. 5219
active WCS 5220

# writes go through G10 L2 / L20; the controller
# computes the values, then the HMI mirrors the row
# index 1..9; file is two columns, sorted by key
# dirty rows persist immediately; malformed lines survive
    Why the filesystem still matters: LinuxCNC only writes the parameter file when the interpreter exits. NmlBackend mirrors changed G54–G59.3 and G92 rows immediately, so a killed session does not lose them. Probe parameters #1001–#1009 come from that same cache because NML does not expose numbered parameters.
    06 / FAILURE DOMAINS
    Crash isolation

    What survives what.

    The separation is deliberate: the machine-facing panel service has a smaller failure domain than the HMI. The native NML link does not. That is the central trade-off of this architecture.

    linc crashes

    The display disappears and the in-process NML link is lost. LinuxCNC keeps running, and linc-panel keeps the physical panel and its HAL pins alive.

    linc-panel crashes

    cnc_panel.* stops updating. The HMI shows a panel-offline condition and fails closed. The serial port is released with the process.

    NML status is lost

    meta.stale is set, the bridge is marked not alive, the last snapshot is retained and the UI must not present it as live state.

    linc-mcp crashes

    No effect on the HMI or the controller. Diagnostics are an observer over Unix sockets, not a participant in the control loop.

    The accepted trade

    The HMI is the shim's failure domain.

    Keeping NML in-process buys a short, direct call path and removes a process, a codec and a runtime. The cost is that a native shim fault can take the screen down with it.

    For a single-seat HMI with a separate panel service, that trade is acceptable. A native machine service would restore isolation but is a substantially larger design: shared-memory snapshots, a typed command socket, supervision and another lifecycle to own.

    Known limits

    Things to remember when changing it

  • !
    One client, one thread. NmlClient is not Sync; do not share it across workers.
  • !
    No numbered parameters over NML. Probe #1001–#1009 are read from the parameter-file cache.
  • !
    Cross builds need target libraries. The arm64 package path needs a target LinuxCNC sysroot, not the host's.
  • !
    Stale processes poison a sim. start-sim.sh cleans old LinuxCNC/LiNC processes when no linuxcncsvr is running.
    • Before · removed

    Supervised Python helper

    python3 + linc_bridge.py used the official linuxcnc and hal modules. The HMI exchanged newline-delimited JSON across a process boundary, for no latency benefit.

    →
    Now · current

    In-process native NML

    NmlClient and HalReader live on the backend worker. Direct typed calls replace JSON lines; the helper and its codec are gone.

    07 / BUILD & RUN
    Dependencies

    Build it, then attach it.

    The simulator profile still links the native NML path into the binary, even though it selects SimBackend at runtime. A real LinuxCNC session supplies the NML channels and HAL memory the backend attaches to.

    To build

    • Rust toolchain and a C++ compiler for the NML shim
    • LinuxCNC development files: /usr/include/linuxcnc, liblinuxcnc.a, libnml.so, liblinuxcncini.so, libtooldata.so
    • The sibling ../linuxcnc-nml checkout (or an equivalent path)
    • liblinuxcnchal.so for HAL reads and typed outputs

    To run

    • A profile: --config or LINC_CONFIG is mandatory
    • A LinuxCNC session running at the profile's INI
    • linc-panel for the physical panel; it owns the serial port
    • linc-mcp only if diagnostics are wanted
    build & smoke-test
    $ cargo build --release
$ cargo test --workspace
$ ./target/release/linc --config configs/sim.toml --check-config

# start LinuxCNC, the panel service and the HMI together
$ ./scripts/start-sim.sh --detach --release-estop --power-on --home
    Cross-compile warning: an arm64 build must link target-side LinuxCNC libraries. The current scripts/build-deb.sh arm64 path needs a target sysroot before it can link the native NML client.
    Simulator note: --sim selects SimBackend at runtime and uses the LINC_SIM_IPC files. The UI, panel service, HAL outputs and diagnostics stay the same; only the machine backend changes.
